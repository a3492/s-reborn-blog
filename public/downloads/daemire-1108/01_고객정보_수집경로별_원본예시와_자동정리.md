# 01. 고객정보는 어디에서 오고, 어떻게 한 표가 될까?

> **읽는 순서:** `00_시작하기_자료사용가이드_최종_v2.md`를 읽은 다음, CRM 엑셀을 열기 **전에 이 문서를 읽는다.** 이 자료에서 고객 상담부터 방문까지 어떤 기록이 남는지 먼저 살펴본다.

## 오늘 배울 것: 엑셀은 출발점이 아니라 도착점이다

고객이 인스타그램에서 문의할 때부터 엑셀 파일이 만들어지는 것은 아니다. 처음에는 **DM 한 줄**, **카카오톡 대화**, **예약 알림**, **전화 메모**처럼 서로 다른 형태로 기록된다. 담당 직원이 필요한 내용만 정리한 후 한 표에 쌓아야 비로소 상담 건수와 예약 전환을 계산할 수 있다.

**한 줄 흐름:** 대화·알림·메모 → 필요한 정보 추출 → 경로별 접수번호 → 중복·동일 고객 확인 → 상담문의 목록 → 방문시술매출 CRM과 연결

> 아래의 채팅·알림·화면은 각 경로의 **업무 모습을 재구성한 예시**다. 실제 서비스의 화면이나 공식 알림 문구를 복제한 것이 아니며, 사용 권한·설정·상품에 따라 보이는 항목과 내보내기 기능은 다르다. 강연용 자료에서 등장하는 김민지·박서준 등은 특정 실제 고객을 지칭하지 않는다.

## 1. 경로별 원본은 이렇게 다르게 들어온다

### A. 카카오톡 채널 상담 — 메시지가 여러 줄로 들어온다

**상담 화면에서 직원이 읽을 법한 대화**

```text
[10/02 (금) 09:42] 민지
안녕하세요~ 어제 인스타에서 보톡스 문의 했었는데요
담주 금욜 예약 가능할까요??

[09:44] 에스리본 상담팀
안녕하세요. 원하시는 시간대가 있으실까요?

[09:47] 민지
오후 4시쯤요. 이름 김민지예요!

[09:52] 에스리본 상담팀
예약 가능 시간 확인 후 안내드릴게요.

[10:08] 에스리본 상담팀
10월 16일 오후 4시로 안내드렸습니다.
```

**지금 알 수 있는 것:** 채널=카카오톡, 표시명=민지, 본인이 말한 이름=김민지, 관심 시술=보톡스, 희망 예약일과 시간. **빠진 것:** 신뢰할 수 있는 전화번호, 동일인 확인 근거, 방문·결제 사실. **주의:** “어제 인스타에서 문의”는 고객의 진술이지 두 계정이 자동 연결되었다는 증거가 아니다.

### B. 인스타그램 DM — 닉네임만 보일 수 있다

```text
10월 1일 10:00
@mint_day92
보톡스 턱쪽 문의요
이번달에 가려고 하는데 상담 먼저 가능할까요?
가격은 대략 얼마예여

상담팀 10:17
안녕하세요. 상담 가능하며 가격과 시술 적합성은 내원 상담 후 안내드립니다.
```

**지금 알 수 있는 것:** 인스타그램 계정 표시명, 문의 시각, 관심 시술, 질문 내용. **빠진 것:** 법적 이름, 연락처, 실제 예약 여부. 위 계정명을 김민지와 연결하려면 고객 확인이 별도로 필요하다. 계정 핸들은 외부 AI 분석 표에 그대로 남기지 않는다.

### C. 네이버 예약 — 대화가 아니라 예약 알림 형식

```text
[예약 알림 / 예시]
새 예약 신청이 접수되었습니다.
예약 일시: 2026-10-21 (수) 15:30
예약자: 박서준
예약 항목: 피부 상담
진행 상태: 신청 / 확인 대기
요청 사항: 모공이랑 흉터 같이 보고 싶어요
```

**지금 알 수 있는 것:** 예약자 표기, 날짜·시간, 예약 항목, 신청 상태, 메모. **빠진 것:** 실제 내원, 결제, 확정 예약 여부(신청 상태만으로 확정이라고 보면 안 됨), 의료 상담 이력. 실제 통지 항목은 설정과 제공 범위에 따라 달라진다.

### D. 전화 상담 — 자동 대화록이 아니라 직원의 메모일 수 있다

```text
10/03 13:21 / 상담팀 A
윤시은 님? (성함 재확인 필요)
필러 상담 요청, 이번 주말은 어려움
담주 월욜 오전 선호
가격 문의하심 / 통화 종료
연락처: 내부 접수 시스템에서 확인 (분석 파일에는 미기재)
```

**지금 알 수 있는 것:** 통화 시각, 직원이 받아 적은 이름·관심 시술·희망 일정. **빠진 것:** 정확한 이름, 확정 예약, 실제 방문, 전체 상담 내용. 통화 기록과 녹취·상담 메모는 별개이며 녹취·보관에 관한 법률과 내부 규정을 따라야 한다.

### E. 구글폼 응답 — 스프레드시트에 한 줄로 들어올 수 있다

```text
제출시간              | 상담희망자 | 관심시술      | 선호시간       | 기타 요청
2026-10-14 14:28     | 안민준     | 스킨부스터     | 저녁 시간      | 통증 심한가요??
```

**지금 알 수 있는 것:** 제출 시각과 **병원이 폼에 만들어 둔 질문의 응답값**. **빠진 것:** 질문하지 않은 정보, 상담원이 실제로 답변했는지, 예약 확정 여부. 이름·연락처를 필수로 설정하지 않았다면 빈칸일 수 있다. 폼과 시트 연결은 별도 설정이 필요하다.

### F. 베가스CRM 입력 — 직원이 정리해 입력하는 내부 업무 화면

```text
[고객/내원 등록 화면을 설명하기 위한 입력 항목 예시]
고객관리번호       P0001
고객명             김민지
방문일             2026-10-16
시술명             보톡스
결제금액           80,000원
방문구분           재방문
최초유입경로       인스타그램 DM
연결문의번호       INQ-202610-0001
[저장]
```

**지금 알 수 있는 것:** 내부에 입력된 고객번호, 내원·시술·결제 내역과 직원이 입력한 연결 정보. **빠진 것:** 인스타그램·카카오톡 원본 대화는 별도 연결·입력이 없다면 CRM에 자동으로 남지 않는다. **중요:** 위 항목은 강연용으로 재구성한 입력 예시다. 베가스CRM의 실제 버전별 화면·필드·자동 연동 기능을 확인한 결과는 아니다.

### 경로마다 있는 정보와 없는 정보

| 원본 경로 | 처음부터 흔히 있는 정보 | 빠지거나 확인이 필요한 정보 | 병원 담당자가 할 일 |
|---|---|---|---|
| 카카오톡 채널 | 대화 시간, 프로필 표시명, 질문 내용 | 실명·전화·예약확정·방문 | 채팅에서 질문·희망 일정 추출 |
| 인스타그램 DM | 계정 표시명, 메시지, 문의 시점 | 실명, 전화번호, 같은 고객 여부 | 상담 내용과 접수 경로 기록 |
| 네이버 예약 | 예약 시점·일정·상태, 제공 범위의 예약자 정보 | 실제 방문과 결제, 임상 상담 내용 | 신청·확정·취소 상태 구분 |
| 전화 | 통화 시각, 직원 메모 | 기록하지 않은 질문, 예약확정, 정확한 이름 | 메모 표준화·누락 확인 |
| 구글폼 | 제출 시각, 폼에 설정한 질문과 답 | 질문하지 않은 항목, 후속 상담 여부 | 시트 연결 및 누락 검토 |
| 베가스CRM | 직원 입력 고객·방문·시술·결제 데이터 | 외부 채널 원문과 자동 연결 보장 없음 | 기록의 정확성과 연결 근거 검증 |

## 2. 서로 다른 원본이 어떻게 상담 목록 한 줄이 되는가?

### 먼저 이해할 원칙: 문의 1건과 고객 1명은 다르다

- **문의 1건:** 고객이 한 번 상담을 시작한 기록. 문의관리번호를 붙인다.
- **고객 1명:** 병원이 확인하여 관리하는 한 사람. 고객관리번호를 붙인다.
- **방문 1건:** 하루에 접수해 시술받거나 진료받은 건. 방문관리번호를 붙인다.
- 같은 사람이 인스타그램으로 묻고 카카오톡으로 예약하면 **원본 접촉은 2개**지만, **고객은 1명**일 수 있다. 각각의 접촉 기록은 지우지 않고 보존한다.

### 김민지 사례: 10월 1일 문의 → 10월 2일 예약 상담 → 10월 16일 방문

**1단계. 인스타그램에서 질문이 들어온다.**

```text
10/01 10:00 @mint_day92: 보톡스 턱쪽 문의요. 상담 먼저 가능할까요?
```

**2단계. 직원이 필요한 칸만 뽑는다.**

| 필요한 칸 | 정리한 값 |
|---|---|
| 이름 | 미확인 (이 시점에는 이름을 모름) |
| 연락처 뒷자리 | 미확인 (애초에 번호를 받지 않음) |
| 경로 | 인스타그램 DM |
| 관심 시술 | 보톡스 |
| 날짜 | 2026-10-01 |
| 문의 내용 | 시술·가격/상담 가능 여부 (분류 확인 필요) |

**3단계. 병원 내부에서 접수번호를 붙인다.**

`IGDM-20261001-001` = 인스타 문의 + 2026년 10월 1일 + 해당 날짜 1번째 기록. 이 번호는 **병원에서 만든 접수번호 예시**이며, 인스타그램이 발급한 원본 메시지 ID가 아니다.

**4단계. 다음 날 카카오톡으로 연락이 온다.**

```text
10/02 09:42 카카오톡 표시명 '민지': 어제 인스타 문의했는데 금욜 오후 4시 예약돼요?
10/02 09:47: 이름 김민지예요.
```

직원은 이 접촉에 `KKO-20261002-001`을 붙여 **별도 상담 접촉 기록**으로 남긴다. 인스타 계정과 카카오 계정이 같은 사람이라는 말만으로 확정 연결하지 않고, **병원 안에서 권한 있는 직원이 고객 동의 및 내부 확인 절차에 따라** 두 문의의 동일 고객 여부를 확인한다. 같은 이름, 같은 시술, 비슷한 시각만으로 연결하면 안 된다. 확인 전에는 `연결대기`, 확인 후에는 내부 고객번호 `P0001`을 두 기록에 연결한다. 확인에 쓰인 휴대전화 원본 등은 별도 보호된 시스템에만 보관한다.

**5단계. 문의는 문의대로, 예약은 예약대로 기록한다.**

| 원본 접촉 | 경로별 접수번호 | 고객관리번호 | 업무 상태 |
|---|---|---|---|
| 10/01 질문 | `IGDM-20261001-001` | `P0001` (확인 후) | 상담 답변완료 |
| 10/02 예약 협의 | `KKO-20261002-001` | `P0001` (확인 후) | 예약 협의·일정 확인 |

**중요:** 이 표의 두 번째 카카오톡 접촉은 **원본에서 통합하는 과정을 보여주기 위한 추가 기록 예시**로, 제공된 `2026년10월_상담문의_목록.csv`에 두 번째 문의 행이 실제 들어 있다는 뜻은 아니다. CSV에서는 인스타그램에서 시작한 **대표 문의 1건**을 관리하며, 카카오톡 예약 협의는 별도의 접촉 이력으로 생각하면 된다. 이 구분이 없으면 학습자료의 실제 행 수와 설명이 달라진다.

**6단계. 확인된 대표 문의가 CSV 한 줄이 된다.**

실제 제공 파일의 첫 번째 행과 일치하는 값이다. `접수시간`과 `담당자`도 이 파일의 칼럼에 맞춰 적었다.

```csv
문의관리번호,경로별접수번호,접수일,접수시간,접수경로,고객명,문의유형,관심시술,처리상태,고객관리번호,예약연결여부,담당자
INQ-202610-0001,IGDM-20261001-001,2026-10-01,10:00,인스타그램 DM,김민지,기타 문의,보톡스,답변완료,P0001,확인됨,상담팀 A
```

여기서 `기타 문의`는 **제공된 CSV에 실제 입력된 분류**다. 원문 대화만 보고 `시술·가격 문의`로 자동 수정하지 않는다. 원문·분류가 달라 보이면 담당자가 확인할 **분류 검토 대상**으로 표시한다.

**7단계. 방문 내역은 CRM에서 따로 기록한다.**

```text
방문관리번호: VIS-202610-0001
고객관리번호: P0001
고객명: 김민지
방문일: 2026-10-16
시술명: 보톡스
결제금액: 80,000원
방문구분: 재방문
연결문의번호: INQ-202610-0001
```

이것은 `2026년10월_방문시술매출_CRM.xlsx`의 첫 번째 방문 기록과 일치한다. **재방문**이므로 최초 고객 등록 이전의 방문 이력이 있을 수 있지만, 현재 보여주는 10월 파일에는 그 과거 방문 내역이 모두 들어 있지 않을 수 있다.

**8단계. 문의→방문을 연결한다.**

`상담문의_목록.csv`의 `문의관리번호`와 CRM의 `연결문의번호`가 같은지 확인하고, **고객관리번호도 일치할 때만** 연결을 인정한다. 연결된 행이 늘어났다면 결제금액을 곧바로 합산하지 말고 **방문관리번호별로 한 번만 계산**한다.

### ID를 붙이는 기준표

| 경로 | 내부 접수번호 예 | 뜻 |
|---|---|---|
| 인스타 DM | `IGDM-20261001-001` | 인스타 문의, 10/01, 순번 001 |
| 카카오 채널 | `KKO-20261002-001` | 카카오 문의, 10/02, 순번 001 |
| 네이버 예약 | `NVR-20261003-001` | 네이버 예약 관련 접수 |
| 전화 | `TEL-20261003-001` | 전화 접수 |
| 구글폼 | `GF-20261014-001` | 폼 제출 접수 |

*주의:* 파일의 기존 `경로별접수번호`에는 `KAKAO-`, `NAVER-`, `CALL-`, `GFORM-`이 사용되어 있다. 위 `KKO-`, `NVR-`, `TEL-`, `GF-`는 **앞으로 사용할 수 있는 간단한 통일안**이다. **기존 CSV에 있는 번호를 임의로 변경해서는 안 된다.** 바꾸려면 옛 번호↔새 번호의 대응표를 만들고, 중복·누락·연결 오류를 검증한 뒤 일괄 변환한다. 서비스 공식 원본 ID가 아니라 병원 내부 ID라는 점도 구분한다.

### 이것만은 외우기

- 한 고객에게 문의가 여러 개일 수 있다. 두 줄을 함부로 하나로 지우지 않는다.
- 이름이 같아도 서로 다른 사람일 수 있다. 이름·전화 뒷자리만으로 자동 병합하지 않는다.
- 원본 메시지와 분석용 표는 따로 관리한다. 외부 AI에는 불필요한 식별정보를 넣지 않는다.
- 문의가 예약으로 이어졌다고 해서 실제 방문했다고 추정하지 않는다.

## 3. 실제로 쌓는 방법 — 가장 쉬운 것부터

### 방법 1. 직원이 하루 끝에 복사해 붙여넣기 (가장 쉬움)

**준비물:** 병원 내부 상담관리 시트, 권한 있는 직원, 기록할 최소 항목(접수일·경로·문의유형·상태·내부 ID).

1. 하루가 끝나면 인스타·카카오·전화 등에서 **당일 처리한 상담 건수와 필수 항목**을 확인한다.
2. 개인정보가 있는 대화 전체를 옮기지 않고, 상담 유형·접수일·상태만 병원 승인 시트에 입력한다.
3. 접수번호 중복, 날짜 누락, 예약 확정/대기 혼동을 확인한다.

**이렇게 나오면 성공**

```text
2026-10-02 | 카카오톡 채널 | 보톡스 | 예약일정 확인 | KKO-20261002-001
```

**주의:** 채널에서 복사가 허용되는 범위인지 확인하고, 원본을 공개 공유 시트로 옮기지 않는다. 원본 연락처와 분석용 표의 관리 위치를 구분한다.

### 방법 2. ChatGPT로 텍스트를 표로 정리하기

**준비물:** 데모용 채팅 텍스트 또는 비식별 처리해도 되는 내부 승인 자료, ChatGPT 파일 첨부 기능 또는 입력창.

1. 대화에서 이름, 계정명, 전체 전화번호, 이메일, 사진 속 개인정보와 민감한 상담 내용을 먼저 삭제하거나 승인된 테스트 사례만 사용한다.
2. 텍스트를 ChatGPT에 붙여 넣고 아래 프롬프트를 그대로 사용한다. 캡처를 쓰는 경우에도 **업로드 전에 이미지 속 식별정보가 제거되었는지** 확인한다.
3. 출력 표와 원본을 사람이 비교해 누락·오해·추측값을 수정한다.

**복붙 프롬프트**

```text
다음은 병원 상담 접수 예시입니다. 상담을 표로 정리해 주세요.
표의 열은 '접수일, 접수경로, 관심시술, 문의유형, 예약상태, 확인필요사항'으로 해 주세요.
없거나 확인되지 않은 정보는 반드시 '미확인'이라고 쓰세요.
이름, 전화번호, 계정명, 생년월일, 주소, 자유서술 의료정보는 출력하지 마세요.
같은 고객인지 추정해서 합치지 마세요. 문의 한 건은 한 줄로 유지하세요.
출력 전에 원문과 표를 대조하여 추측해서 채운 값이 있는지 알려 주세요.

[여기에 식별정보를 제거한 상담 텍스트를 붙여 넣으세요]
```

**이렇게 나오면 성공:** `2026-10-01 | 인스타그램 DM | 보톡스 | 시술·가격 문의(검토 필요) | 미확인 | 실명·예약 여부 미확인`처럼 검토 여부가 표시된다.

**주의:** ChatGPT가 틀린 날짜를 만들어 내거나 질문만 했는데 예약 확정으로 표시할 수 있다. 반드시 원문과 대조한다. 실제 환자 상담 원문은 외부 서비스에 무단 업로드하지 않는다.

### 방법 3. 구글폼 → 구글시트 자동 누적

**준비물:** 병원에서 관리하는 Google 계정, Google Forms, Google Sheets, 적절한 접근 권한.

1. 구글폼을 만들고 `접수일`, `관심시술`, `희망연락시간` 등 **필요한 최소 질문**을 넣는다. 환자에게 민감한 의료정보를 자유롭게 쓰게 하는 항목은 만들지 않는다.
2. 구글폼의 **응답** 메뉴에서 Google Sheets에 응답을 연결한다.
3. 시험 응답을 한 번 제출하고 시트에 새 행이 쌓이는지 확인한다.

**이렇게 나오면 성공:** 제출 시각과 응답이 시트의 새 행으로 자동 추가된다.

**주의:** 폼을 시트에 연결하면 **폼 응답만** 자동 쌓인다. 인스타 DM·카카오톡·CRM 기록까지 저절로 들어오지 않는다. 개인·민감정보 수집 시 적법한 고지·동의·보관·접근제어 등을 별도로 검토해야 한다.

### 방법 4. 카카오 채널·네이버 예약의 제공 내보내기 기능 활용

**준비물:** 관리자 권한, 서비스 관리자 화면, 해당 상품·계정에서 제공하는 공식 다운로드 또는 보고서 기능 확인.

1. 카카오 채널·네이버 예약 관리자에서 **현재 계정이 제공하는** 상담·예약 내역 열람 또는 다운로드 기능을 찾는다.
2. 실제로 내보낼 수 있는 자료가 있다면 필요한 기간과 항목만 추출한다. 없으면 직원이 접근 가능한 화면에서 허용된 방식으로 최소 정보를 기록한다.
3. 날짜·상태·중복을 확인한 뒤 내부 관리 시트의 공통 열 이름으로 옮긴다.

**이렇게 나오면 성공:** `접수일 | 경로 | 문의유형 | 예약상태 | 내부접수번호` 형태로 통일된 행이 만들어진다.

**주의:** **모든 카카오 채널 대화나 네이버 예약 데이터가 CSV로 일괄 내보내기 가능하다는 뜻이 아니다.** 상품·권한·정책·화면에 따라 다르다. 공식 API 사용이나 자동 수집이 가능하다고 전제하지 않는다. 비공식 스크래핑은 이용약관 및 보안 위험을 먼저 검토한다.

### 방법 5. Zapier·Make 같은 자동화 도구 연결 (나중 단계)

**준비물:** 접수 표준, 사용 가능한 공식 연동 또는 API, 테스트 계정, 병원 정보보안·개인정보 처리 검토, 오류 확인 담당자.

1. **자동 연결이 허용되고 실제 지원되는 경로부터** 정한다. 예: 구글폼 새 응답 → 병원 내부 승인 시트에 한 행 생성.
2. 시험 기록 5건으로 연결하고 각 행에 중복방지 키와 처리 시각을 남긴다.
3. 중복 생성·전송 실패·개인정보 노출 여부를 확인한 뒤 운영 범위를 천천히 넓힌다.

**이렇게 나오면 성공:** 시험 폼 5건을 입력했을 때 승인 시트에 정확히 5행이 추가되며, 다시 실행해도 중복 5행이 생기지 않는다.

**주의:** Zapier·Make가 인스타 DM, 카카오톡, 네이버 예약, 베가스CRM에 **모두 직접 연결되는 것은 아니다.** 실제 커넥터·API·인증·계약 조건 확인이 먼저다. 원본 의료·개인정보를 외부 자동화 도구로 보낼 경우 적법성·처리위탁/국외이전 여부·접근 권한·로그·보존기간·보안조치를 검토해야 한다.

## 4. 직원이 가장 자주 막히는 경우

| 막히는 상황 | 왜 그런가 | 해결 방법 |
|---|---|---|
| 고객 이름이 DM에 없다 | 계정명만 보일 수 있다 | `미확인`으로 남기고 내부 업무에서만 신원 확인 |
| 인스타와 카카오가 같은 고객인지 모른다 | 각 서비스 계정이 다르다 | 검증 전에는 별도 문의, 확인 후에만 내부 고객번호 연결 |
| 같은 사람의 문의가 두 건으로 보인다 | 문의 2회는 정상적으로 2건일 수 있다 | 문의 건수와 고객 수를 따로 계산 |
| 예약 알림이 와서 방문한 줄 알았다 | 신청·확정과 실제 내원이 다르다 | 방문은 CRM의 내원 기록으로 확인 |
| 전화 상담이 시트에 없다 | 직원 메모가 별도로 저장되었다 | 하루 마감 점검표와 누락 체크 |
| AI가 없는 내용을 채운다 | 추론으로 빈칸을 보충했다 | '미확인' 유지, 출처 대조 프롬프트 사용 |
| 연결 후 결제 매출이 늘어난다 | 한 방문이 여러 문의와 붙었다 | 방문관리번호별 중복 제거 후 금액 계산 |

## 5. 강연에서 이 파일은 언제 보는가?

**강연 1(CRM)의 앞부분, 데이터가 이미 모여 있는 CRM 엑셀을 처음 열기 직전**에 이 파일을 먼저 보여준다. “자료는 원래 엑셀로 태어나는 것이 아니다”라는 메시지로 6개 경로의 원본을 비교하고, 김민지 사례를 따라가며 `2026년10월_상담문의_목록.csv` 1행과 CRM 방문 1행이 만들어지는 과정을 보여준 뒤 본 분석 실습으로 넘어간다.

### 청중의 마지막 30초 확인

- [ ] DM·채팅·알림·전화 메모가 각각 어떤 모습인지 안다.
- [ ] 문의 한 건·고객 한 명·방문 한 건이 다른 단위임을 설명할 수 있다.
- [ ] 경로별 접수번호는 서비스 공식 ID와 구별해야 함을 안다.
- [ ] 같은 사람을 연결할 때 확인 근거가 필요하다는 것을 안다.
- [ ] 외부 AI에 실제 환자의 이름·전체 전화번호·상담 원문을 그대로 보내지 않는다.
