아래 사례는 설명을 위한 가상의 상황입니다.

시연 직전, 화면 위에 ‘준비 완료’가 떴다. 서진이 원본을 열어 보니 일정표만 있었고, 야간 전달 사항 파일은 비어 있었다. RoundPrep 팀이 앞 단계의 실패를 다음 단계에 알리지 않은 탓이다. “완료 표시를 누가, 어떤 조건으로 켜죠?” 혜준이 묻자 팀은 코드를 닫고 작업 순서를 다시 그렸다.

**한 줄 요약.** 단계 사이의 의존성, 갈라지는 조건, 사람이 인계받을 지점을 먼저 정하면 다섯 패턴 중 필요한 것을 고를 수 있다.

## 왜 작업 흐름을 먼저 그릴까

톡에 “오늘 브리핑 만들어 줘”라고 한 번 부탁하는 것과 달리, 매일 같은 결과물을 만들려면 자료 준비, 초안 작성, 승인 중 어디까지 끝났는지 다른 사람도 알아야 한다. 전달 메모가 오지 않았는데 AI가 그럴듯한 초안을 만들어도, 자료가 온 것처럼 공유해선 안 된다. 워크플로우 패턴은 이런 **작업 사이의 약속**을 눈에 보이게 정리하는 방법이다.

그림에서 수정 전후의 입력은 같다. 점검 위치를 바꿔 결과가 달라졌다. 실패한 자료를 발견하는 규칙을 초안보다 앞에 두면, 프롬프트 문장이나 모델을 바꾸지 않아도 문제를 막을 수 있다.

## 흐름을 결정하는 다섯 질문

| 확인할 질문 | 패턴 | RoundPrep의 연습용 예 |
| --- | --- | --- |
| 앞 단계의 결과가 필요한가? | 체인 | 일정표 정리 → 항목 검증 → 공유용 초안 작성 |
| 서로 기다릴 이유가 없는가? | 병렬화 | 일정과 전달 사항을 따로 수집한 뒤 출처 표시를 붙여 합치기 |
| 입력 종류에 따라 절차가 다른가? | 라우팅 | 일정 변경은 일정 담당, 분류가 모호하면 공용 검토함 |
| 자료를 본 뒤에야 할 일이 정해지는가? | 오케스트레이터–서브에이전트 | 누락 보고서를 읽고 필요한 자료만 하위 작업으로 요청 |
| 같은 체크리스트로 보완할 수 있는가? | 평가–수정 | 필수 항목 누락만 수정하고, 반복 한도를 넘으면 담당자에게 넘기기 |

**체인과 병렬화.** 공유용 초안은 입력 검증이 끝난 뒤에 만든다. 반면 일정표와 전달 사항은 동시에 가져와도 된다. 두 자료 중 하나가 누락되면 정상 완료와 구별해 ‘일부 자료 없음’ 상태를 남긴다.

**라우팅과 위임.** 라우팅은 정해진 목적지 중 한 곳으로 보낸다. 위임은 자료를 읽은 뒤 필요한 하위 작업부터 정한다. 경로가 예측 가능하면 라우팅부터 적용하고, 위임을 쓰면 하위 작업이 읽을 수 있는 자료와 종료 조건을 따로 적는다.

**평가–수정.** 평가 단계에 “더 좋은 글을 써라” 대신 “각 항목의 출처와 확인 상태가 있는지 검사하라”고 요청한다. 같은 누락이 반복되거나 원본 자체가 없으면 초안을 보류한다. 여러 모델의 답이 일치해도 같은 근거를 잘못 읽을 수 있다. 의견 불일치는 사람이 들여다볼 신호로 쓰고, 모델의 표 수를 임상 판단의 근거로 삼지 않는다.

## 한 흐름을 먼저 그려 본다

팀은 일정표·전달 사항에 대해 다음 네 줄을 적었다. 바로 따라 해 볼 수 있는 설계 초안이다.

1. **입력** — 합성 일정표와 합성 전달 메모. 두 자료를 별도로 읽는다.
2. **출력** — 각 항목에 출처와 확인 상태가 붙은 내부 브리핑 초안.
3. **실패** — 메모가 없으면 ‘미수신’이라고 표시하고 자동 공유를 멈춘다.
4. **승인** — 담당자가 원본과 초안을 대조한 뒤 공유 여부를 결정한다.

다음 시연에서 메모가 비자 화면에 ‘미수신’이 떴다. 팀은 누락의 위치와 재개할 단계를 바로 찾았다. 패턴 선택이 잘됐는지는 이렇게 **실패를 일부러 만들었을 때** 드러난다.

## 한 번씩 실패를 넣어 패턴을 고른다

도구를 연결하기 전에 종이 두 장을 놓고 연습해 보자. 일정표에는 ‘9시 회의실 확인’, 전달 메모에는 ‘회의실 변경’이라고 적는다. 담당자 한 명이 두 장을 번갈아 빼면서 상태를 기록한다.

- **둘 다 있음** — 어느 자료에 어떤 말이 있는지 초안에 남긴다. 담당자가 두 원본을 대조하고 공유한다.
- **메모만 없음** — 일정표 확인 결과는 남겨 두고, 초안을 공유하지 않는다. 메모가 도착하면 그 단계만 다시 확인한다.
- **요청 종류가 모호함** — 일정 변경과 일반 공지를 섞어 넣고, 자동 분류로 결론을 내리지 않는지 검증한다.

이제 어떤 단계가 다음 단계를 기다려야 하는지 표시해 보자. 초안이 자료 확인을 기다리는 구간은 체인이고, 파일을 따로 확인하는 구간은 병렬이다. 모호한 요청을 검토함에 보내면 라우팅이다. 빠진 항목을 본 뒤에야 추가 작업을 고르는 경우에 위임을 고려한다. 평가·수정은 빠진 원본을 상상해 보충하는 데 쓰지 않는다. 원본을 확보한 뒤 출처 표시 같은 정해진 기준을 검사하는 데 쓴다. 작업을 더 작게 나누는 연습은 [태스크 분해](/blog/orchestration/task-decomposition/)에서 이어서 할 수 있다.
